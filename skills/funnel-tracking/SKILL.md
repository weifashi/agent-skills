# 埋点和漏斗统计：从设计到看数

> 由一个多端产品（官网 + 商家后台 + 收银端）的自有统计沉淀出来：二十多个事件、十二步漏斗、一套运营报表。每条规则背后都是一次真实的返工。
> 案例见 `references/case-study.md`。

核心只有一句话：**埋点是为了做决定。每个事件都要说得出「看到这个数会改什么」，说不出就不埋。**

## 0. 开工：先问清这几件事

> 开工时用户的原话和填好的开工表存进项目 `docs/background/`，拍板的事记进 `docs/decisions.md`（目录约定见 project 技能）；调研报告这类产出也放进项目 `docs/`，不只留在对话里。


清单和可以直接转发给 AI 的任务单见 `references/kickoff.md`。

- 要用数据做哪几个决定（改哪一页、砍哪个渠道、修哪一步）
- 用第三方统计还是自己存：默认建议**自己存**（数据在自己手里、没有第三方脚本、口径自己定），除非团队已经深度依赖某个平台
- 目标国家和它的隐私法（决定同意框怎么做）
- 产品有哪几端（官网、后台、App、给终端顾客用的页面）
- 报表给谁看、在哪看
- 以后投不投广告、投哪家

## 1. 设计：从漏斗倒推事件

做法和模板见 `references/events.md`。

1. **先画漏斗**：从「来到官网」到「付费」，中间每一步都是一个看得见的动作，10 步左右。产品里的「激活」要有明确定义（例如第一笔真实收款）。
2. **一步一个事件**，再补三类：页面类（打开、离开、滚到哪）、意向类（点了哪个按钮、展开了哪个问题）、健康类（用户看到的报错、脚本出错）。
3. **逐个事件过一遍**：留、改、删、加，每个都写「用来做什么决定」。重复的、只是好奇的删掉。
4. **事件字典进代码库**：事件名、哪一端发、带哪些字段、口径。之后加功能就在这里加一行。

事件带的字段要少而固定（枚举值、数字），不带自由文本、金额、姓名、搜索词、聊天原话。

## 2. 身份和同意：三级，各管各的

细则见 `references/privacy.md`。

| 级别 | 是什么 | 要不要同意 | 能算出什么 |
|---|---|---|---|
| 单次打开编号 | 每次打开页面随机生成，只在内存里 | 不要（不写本机、不识别个人） | 每页被看几次、看到哪、点了什么 |
| 访客编号 | 同意后才写进本机的随机编号 | 要 | 同一个人的几次访问、之后注册连成一条路线 |
| 账号 / 店铺 | 后端从登录状态里核对出来的 | 按产品的隐私说明 | 注册后的使用、留存、付费 |

- 同意框只有「拒绝 / 同意」两个一样大的按钮；没选之前不写任何非必要记录；浏览器的全局隐私控制当作拒绝。
- 广告来源参数（utm 等）跟着站内链接一路带进产品，但**写进本机也要等同意**。
- 明确不记：IP、浏览器型号、邮箱、地址栏参数、表单里的自由文本、金额。
- 给终端顾客用的页面（例如扫码点餐）不统计：他们不是你的用户，是你客户的客人。

## 3. 收集接口：默认不信任任何请求

做法见 `references/intake.md`。统计接口是公开的，谁都能往里发：

- **白名单**：每一端只收它该发的事件名；未知事件丢掉并计数，不报错。
- **里程碑事件要验证身份**：注册成功、第一笔收款、升级付费这类事件，只有带着有效登录、并且是本人账号时才收。否则任何人都能把漏斗刷高。
- **限流和限量**：每个来源每天的批数、条数、字节数有上限；全站每天也有上限。统计不能把业务数据库写满。
- **去重**：每个事件带客户端生成的编号；里程碑事件每个账号只记一次。
- **过滤**：机器人、自己人的设备、测试环境分开。
- **保存期限**：定一个天数（例如 400 天），定时清理。
- **永远不影响页面**：统计请求失败、接口没上线，页面照常工作。

## 4. 报表：每个页签对应一个决定

见 `references/reports.md`。

| 页签 | 看什么 | 用来做什么决定 |
|---|---|---|
| 漏斗 | 每一步还剩多少人、停在哪一步的人最多 | 先修流失最大的一步 |
| 按来源 | 各渠道、广告系列、落地页、合作伙伴的访问到付费；加上花费就是每个客户的成本 | 加预算还是停掉 |
| 落地页 | 每页的打开、看到一半、点主按钮、停留、秒退；每一屏还剩多少人 | 改哪一页、哪一屏 |
| 访客路线 | 单个访客或账号的完整时间线 | 看具体的人卡在哪 |
| 产品使用和报错 | 各页面停留、用户看到的报错 | 修哪个功能 |
| 留存 | 注册后第几天还在用 | 产品留不留得住人 |

再加两样：**一键导出给 AI 分析**（数据 + 每个数字的口径 + 分析要求）和**每周周报**。

## 5. 广告转化回传（要投广告时才做）

见 `references/ads.md`。三层分开：自己的统计什么都记；回传只送「真正有结果」的一两个事件；广告平台只拿这一两个信号去找相似的人。不要把十几个行为都设成转化。

## 6. 上线和验证

见 `references/release.md`。要点：建表要用户点头；前端先发是安全的，接口和建表要一起发；用带真实浏览器标识的请求验证入库；上线前自己人测试产生的脏数据要清理，清理前备份。

## 7. 汇报

- 向用户讲埋点时用「谁从哪来、走到哪一步、在哪走掉」这样的话，不讲事件名。
- 事件表里每一行都有「用来做什么决定」一列。
- 明说哪些数现在还看不到（功能没接通、样本太少、没人同意所以连不成路线）。
