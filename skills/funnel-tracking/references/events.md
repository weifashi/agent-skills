# 事件设计：从漏斗倒推

## 1. 先画漏斗

从第一次接触到付费，每一步是一个看得见的动作。例（一个商家用的 SaaS）：

| 步 | 名字 | 怎么算到这一步 |
|---|---|---|
| 1 | 来到官网 | 官网的打开页面事件 |
| 2 | 往下看了一半 | 滚动到 50% |
| 3 | 点了主按钮 | 点击事件，按钮是「免费开始」 |
| 4 | 打开登录页 | 产品里打开页面事件，路径是登录页 |
| 5 | 收到登录码 | 登录码发送成功 |
| 6 | 开始注册 | 进入注册流程 |
| 7 | 注册完成 | 账号 / 店铺建好 |
| 8 | 完成准备 | 开始使用前必须做的设置做完了 |
| 9 | 第一次真实使用 | **激活**，例如第一笔真实收款 |
| 10 | 用了 3 天以上 | 有 3 个不同的日子在用 |
| 11 | 付费 | 升级到付费套餐 |

要点：

- **每一步之间不要有黑洞**。「点了主按钮」到「注册完成」之间如果没有登录页和登录码这两步，就看不出人是卡在收验证码上还是别处。
- **激活要是真实使用**，测试数据、示例数据不算。
- 漏斗前半段数的是「人次」（没同意的访客每次打开都是新的），后半段数的是账号。报表里要把这一点写清楚。
- 加了新的关键功能（例如接硬件），在对应位置加一步。

## 2. 三类辅助事件

| 类 | 事件 | 用来做什么 |
|---|---|---|
| 页面 | 打开页面、离开页面（带实际停留秒数和最远滚动）、看到第几屏、滚动深度 | 哪一页、哪一屏留不住人 |
| 意向 | 点了哪个按钮（带按钮在页面的哪一块）、展开了哪个常见问题、切换语言、看演示视频 | 用户关心什么、担心什么 |
| 健康 | 用户看到的报错提示、页面脚本出错 | 哪里坏了 |

- 「离开页面」里，切到别的标签页的时间不算停留。
- 「切换语言」多，说明投放的语言或默认语言不对。
- 「展开的常见问题」等于用户直接告诉你他在担心什么。

## 3. 逐个过一遍

把现有的和打算加的事件排成一张表，每行写结论和原因：

| 事件 | 结论 | 原因 |
|---|---|---|
| 轮播图点了第几张 | 删除 | 对改页面没有帮助，只是噪音 |
| 导航锚点点击 | 删除 | 和「看到第几屏」重复 |
| 同意框选择 | 保留，改口径 | 原来每打开一页就记一次，同意率被算高了；改成只在亲手点选时记 |
| 离开页面 | 新增 | 没有它就算不出停留时间和秒退 |
| 登录码发送、登录完成 | 新增 | 原来登录页完全没数据，是漏斗中间的黑洞 |

判断标准只有一条：**看到这个数会改什么**。答不上来就删。

## 4. 事件带什么

每个事件的固定信息：

- 事件编号（客户端生成，用来去重）、发生时间
- 哪一端、事件名
- 单次打开编号；访客编号（同意后才有）；账号编号（后端核对后才记）
- 页面路径（**去掉参数**）、页面编号、语言
- 来源：从哪个网站来（只记域名）、utm 各项、落地页编号、合作伙伴编号

事件自己的字段（props）：

- 数量有上限（例如 12 个），每个值限长。
- 只用枚举值和数字：`place: hero / pricing / footer`、`percent: 50`、`via: lan / cloud`。
- 不带：金额、姓名、邮箱、电话、商品名、搜索词、聊天或语音的原文、设备序列号。
- 需要带文字的只有报错提示，入库前去掉链接和邮箱。

## 5. 里程碑事件只记一次

注册完成、第一次使用、付费这类事件，每个账号一辈子只该有一条。客户端和服务端都要防重复：

- 客户端：本机记一个「已经发过」的标记，按账号区分；刷新、重新登录不再发。
- 服务端：同一账号同一里程碑只留第一条。

没做这一条的后果：测试时一家店被记了二十多次「注册完成」，漏斗完全失真。

## 6. 事件字典

写成一份文档放进代码库，一个事件一行：

| 事件名 | 哪一端 | 什么时候发 | 字段 | 用来做什么 | 加入日期 |
|---|---|---|---|---|---|

之后每做一个新功能，上线前问一句「这个功能有没有人用，统计里看得到吗」。看不到就在这里加一行，并同步到收集接口的白名单。
