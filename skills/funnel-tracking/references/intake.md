# 收集接口：默认不信任任何请求

统计接口必须对未登录的访客开放，所以它是整个系统里最容易被滥用的入口。按下面几条做。表结构示例见 `assets/schema.example.sql`，前端脚本示例见 `assets/track.example.js`。

## 接口形状

- 一个接口，`POST /events`，一次收一批（上限例如 25 条）。
- 永远快速返回，返回「收了几条、丢了几条」。客户端不根据返回做任何业务判断。
- 客户端用 `sendBeacon` 或 `fetch(..., {keepalive: true})` 发，页面关闭时也能发出去。

## 校验

逐条校验，不合格的丢掉并计入「丢弃数」，不让整批失败：

| 校验 | 说明 |
|---|---|
| 事件名白名单 | 按端分：官网只能发官网的事件，后台只能发后台的。未知事件丢掉 |
| 字段白名单 | 多出来的字段直接拒绝 |
| 编号格式 | 事件编号、单次打开编号、访客编号都必须是标准的随机编号格式 |
| 文本 | 限长；不许有控制字符；路径去掉参数 |
| 时间 | 发生时间不能比现在早太多（例如 7 天）或晚太多（例如 5 分钟） |
| 字段个数和大小 | props 最多若干个键，值只能是短字符串、数字、布尔 |

需要保留的少量自由文本（用户看到的报错提示）入库前清洗：去掉链接、邮箱、控制字符。这些文字会出现在内部后台和周报邮件里，不清洗就可能被人塞进钓鱼网址。

## 关键事件要验证身份

把事件分三种：

| 种类 | 例子 | 谁能发 |
|---|---|---|
| 页面和意向类 | 打开页面、点击、滚动 | 谁都能发 |
| 登录后才会发生的 | 登录完成、开始注册 | 请求里要有有效登录；每个账号每天限条数 |
| 里程碑 | 注册完成、第一次使用、付费 | 请求里要有有效登录，**并且**事件里的账号就是登录的这个账号 |

不这样做，任何人写个脚本就能把「付费」刷到一万，报表和按它做的决定全都失效。

发生在登录之前、没法验证的事件（例如「登录码已发送」），按来源每天限一个较小的数，和业务本身的上限保持一致。

设备端（例如收银机、平板）没有人的登录，用设备自己的凭据来证明「我是这个账号下的设备」。

## 限流和限量

统计表常和业务数据放在同一个数据库。统计被刷爆，不能连累登录和业务：

- 每个来源：每分钟的请求数、每天的批数、每天的条数、每天的字节数。
- 全站：每天的条数和字节数（按「保存天数 × 每天上限」算出最坏情况下占多少空间，定一个能接受的数）。
- 只限条数不够：每条都塞满时，同样的条数能占几十倍的空间，所以还要按字节限。
- 超限时只丢统计、照常返回成功，不报错、不影响页面。

## 过滤

- **机器人**：按浏览器标识里的关键词过滤（bot、crawl、headless、curl 等）。注意自动化测试用的无头浏览器也会被滤掉，验证入库要用带真实浏览器标识的请求。
- **自己人**：客户端的「内部设备」标记 + 后端识别内部后台的登录。
- **环境**：测试和正式各用各的库，测试点击不混进正式数据。

如果接口前面有一层网关或转发，确认它把浏览器标识原样传到后端。否则所有请求都会被当成机器人丢掉，表面上一切正常，库里却一条都没有。

## 存储

- 一张事件表，一行一个事件；固定列放常用的查询维度，其余进一个 JSON 列。
- 按时间、事件名、访客、账号建索引。
- 另有一张「访客编号 ↔ 账号」的对应表，注册完成时写入。
- 定时任务按保存期限清理。

## 兼容性

前端和后端不一定同时发布，所以：

- 后端遇到不认识的事件：丢掉、计数、不报错。这样前端可以先发。
- 前端遇到接口不存在或报错：静默，不重试到影响页面。
- 需要新表的后端功能，要和建表一起发，否则相关报表会报错。
