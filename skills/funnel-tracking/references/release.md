# 上线和验证

## 上线顺序

| 部分 | 注意 |
|---|---|
| 建表 | 属于数据库变更，要用户明确同意，不算在「改完就发」的默认授权里。只新建表、不改已有表，风险最小 |
| 后端接口 | 和它依赖的表一起发。只发接口不建表，相关报表会报错 |
| 前端脚本 | 可以先发。后端还没上时，请求只会得到 404，页面不受影响 |
| 报表页面 | 需要内部后台能登录。登录没配好的话，数据在收，但没人看得到——要提前确认 |

多人或多个 AI 会话共用一个仓库时，说清楚谁负责发后端；交接文档里写明「要执行哪个建表文件、发哪些文件、怎么验收」。

## 验证

逐项做，结果如实记录：

1. **发一条合格的事件，确认入库。** 用带真实浏览器标识的请求。无头浏览器和命令行工具默认的标识会被当成机器人滤掉，返回成功但库里没有——这是设计，不是故障。
2. **发几条不合格的，确认被丢掉。** 未知事件名、多余字段、过期的时间、伪造的里程碑（不带登录）。
3. **走一遍真实流程**：带着来源参数打开落地页 → 点主按钮 → 注册 → 第一次使用。然后在报表里找到这条路线，看来源有没有一路带过来。
4. **同意框**：拒绝后检查本机没有访客编号和来源记录；同意后才有；撤回后被删掉。
5. **里程碑不重复**：刷新、退出重新登录几次，报表里这个账号的「注册完成」还是 1。
6. **自己人不统计**：打开内部标记后，再操作一遍，库里没有新增。
7. **限量**：确认超限时只丢统计、接口照常返回、页面不受影响。

有后端缓存或常驻实例的平台，发布后旧代码可能还会跑几分钟。验证前先确认新代码已经生效，否则会把「还没切过去」误判成「改错了」。

## 上线前的脏数据

开发和测试阶段，自己人反复刷新、重新登录，会留下大量重复记录。正式看数之前：

1. 数清楚要清的范围和条数（例如「修复版上线之前、来自后台和收银端的 199 条」）。
2. 告诉用户，等同意。
3. 清之前把这些行备份到本机（不进代码库）。
4. 只删统计表里的行，不动任何业务数据。
5. 清完说明报表会有什么变化（例如某一步暂时变成 0）。

## 交付时要说清的

- 事件表（每个事件用来做什么决定）在代码库的哪个文件。
- 报表在哪看、谁能看。
- 现在还看不到的数，以及原因（功能没接通、样本太少、还没有人同意所以连不成路线）。
- 需要法务确认的点、公司层面的合规事项。
- 自己人怎么把设备标记成不统计。
