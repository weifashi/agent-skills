# 一页 HTML：需求原型 / 高保真效果图 / 改动汇报

**让人看图就懂，字只做标注。** 读的人多半不是技术人员，也没空读长文：每一节先给一张图（界面、流程、对比），再用一两句话点出看哪里。凡是「改」，都画成 **改前 → 改后**。

| 用法 | 讲的是 | 起手 | 细则 |
|---|---|---|---|
| **A 需求原型** | 要做成什么样、几个方案怎么选 | `assets/template.html` + `assets/blocks.html` | 本文件 |
| **B 改动汇报** | 已经改了什么、谁受影响 | 同上，正文栏用 `.wrap rep` | **先读 `references/change-report.md`** |
| **C 高保真效果图** | 做出来长什么样、怎么一步步用（给老板、客户） | `assets/hifi.html` | 读 `references/hifi.md` |

A 和 C 可以合在一页。要真能提交数据、要 1:1 对齐线上组件的，不走本技能。

## 图为主、字为辅

先想「这件事画成什么图」再动手。想不出怎么画的内容，多半不该放在正文里。

| 要讲的事 | 画成什么 | 积木 |
|---|---|---|
| 改已有的界面、文案、规则 | **改前 / 改后并排两帧**，改动处绿框，其余原样照画 | F |
| 新功能怎么用 | 一步一帧的步骤条，每步一句「点了什么 → 看到什么」 | N（给客户看用高保真） |
| 几个方案让人挑 | 并排画出来 + 一张对比表 + 标出推荐 | F、对比表 |
| 什么情况得到什么结果 | 矩阵表；分支多就画判定流程图 | E、L |
| 状态怎么变、请求怎么走 | 流转图 | 流转图、L |
| 谁在什么时候做了什么 | 时间线 | D |
| 多少、差多少、占多少 | 数字条、条形图 | M、条形图 |
| 没有界面的改动（接口、定时任务、性能） | 流程图 + 同一个操作改前 / 改后的结果对比 | L、对比表 |
| 结论、给谁用、下一步 | 一页看懂，放在最前 | 0 |
| 要对方定的事 | 待拍板卡：一张卡一件事，推荐的答案写大字 | P |
| 评审才查的细节（文件、字段、代码位置、数据来源） | 默认折叠 | Q |

积木在 `assets/blocks.html`，索引见 `references/blocks.md`；抄积木时连它的 CSS 一起抄。

**字的规矩**

- 每节 = 一句说结论的小标题 + 图 + 至多两行说明。写不下就拆节，或收进折叠。
- 规则贴着图写：图上标 ①②③，旁边同编号各一句。不写成段落，不另开一节「规则说明」。
- 说对方的话：页面名、按钮名、看到的结果。函数名、文件路径、表名只出现在折叠细节里。
- 一件事只说一遍：图里看得出的不再用文字复述，前面讲过的结论后面不重复。
- 信息不删，只挪位置：评审要查的细节一条不少，默认收起。
- **自查**：遮住文字只看图，要说得出「这页讲什么、改了哪里、要我定什么」。说不出就是图不够，补图，别补字。

## 存哪、怎么给人看

- **正本在项目里**：`docs/mockups/<slug>/index.html`（改动汇报用 `<slug>-changes`），slug 用功能的英文短名。同一件事只有一份：先 `ls docs/mockups/`，有旧的就改那一份，并在页头下加绿色「本次更新」框。
- **给人看**，用第一个可行的：对话内预览工具 → 用户规则里写的预览服务（给完整的公网地址，改过带 `?v=N`，先 `curl` 确认 200）→ 文件路径。
- 不自作主张起服务、开端口、往外传；没有链接就说没有。

## 硬规矩

- **单文件、零外部依赖**：CSS 内联、系统字体、图用内联 SVG，不引 CDN、外部字体、外链图片。`<a href>` 是导航，不算。图标用 ✓ ✕ › ① ★ 这类符号，不用彩色 emoji（很多机器上会变成方块）。
- **从 `assets/template.html` 起手**，不抄旧页面的 `<style>`。
- **先查真实素材再画**：需求原话（项目 `docs/background/`）、现有界面、字段和状态的真名。没核实的标「待确认」。
- **界面帧里只放界面上真有的字**；解释写在帧外。
- **正文 16px 起**；流程图必须真的显示成图，只贴 mermaid 源码不算。
- **颜色有固定含义**：现状灰白 · 这次新增或改的绿 `#16a34a` · 主按钮琥珀 `#f59e0b` · 警告和删除红 `#dc2626`。整页浅色，只有 mermaid 图用黑底。
- **宽度**：原型用 `.wrap`（900px），宽内容加 `.bleed`；改动汇报用 `.wrap rep`（跟着屏幕变宽）；画完整后台用 `.wrap desk`。
- **ASCII** 放 `<pre class="ascii">`，框线里只放半角。mermaid 照积木 L 写，源码里的 `<br/>` 写成 `&lt;br/&gt;`。

## A 需求原型

页面从上到下：

1. 页头：功能名 + 一句话 + 日期 + 「方案 · 未实施」
2. 一页看懂（方案页、调研页才要）
3. 正文：一节一件事，按上表选图；界面超过 3 个加吸顶导航
4. 待拍板卡（有要对方定的事才要）
5. 折叠细节

方案就是方案：不写「已上线」「验证通过」。

## B 改动汇报

手册在 `references/change-report.md`。不能违反的：

1. **不漏**：以 `git diff --name-status` 为底账，每个文件都出现在（折叠的）文件树里。
2. **逐行看**：每处改动归到「规则变了 / 规则没变 / 待确认」，纯重构不编成规则变化。
3. **每条改动一张「改前 → 改后」**：画出页面，配一行「页面 → 操作 → 结果」。用户无感知的也写清变的是什么。
4. **四样必有**：表字段、规则变化、影响谁、怎么回滚。没有就写「无」。
5. 改动小就自己读完；改动大（约 15 个文件或 800 行以上）才分头派代理。

## 检查

```bash
python3 <技能目录>/assets/hifi/inline.py <页面>           # 只有用了高保真零件才跑
python3 <技能目录>/scripts/render-mermaid.py <页面>       # 有 mermaid 才跑，先渲染再量
python3 <技能目录>/scripts/check-overflow.py <页面> --screenshots=<截图目录>
```

- 溢出检查量 390 / 768 / 1440 三种宽度。`FAIL` 行会写明是哪个元素、哪段字；`note` 行只是提示，不用返工。
- 检查通过后**看一张电脑宽度的整页截图**。高保真和要给客户看的页面，再加看手机宽度。
- 缺 Chrome、Node 22 或 `mmdc` 时照实说「未验证 / 图未渲染」，要不要安装先问用户。

## 交付

三句话说清：存在哪（有链接就把完整地址明文贴出）、是方案还是已实施的改动、检查了什么和没检查什么。提到某个界面说它的名字或给锚点。

## 易错点

| 坑 | 正确做法 |
|---|---|
| 一节里写了三四段话 | 换成图 + 标注；细节进折叠 |
| 讲「改」只画了改后 | 改前、改后并排，读的人才知道变了什么 |
| 同一需求新建一个目录 | 改原来那份，旧链接才不会指向旧内容 |
| 凭印象画现有界面、自己编字段名 | 先查代码和截图，用系统里的真名 |
| 界面帧里写讲解文字 | 对方会以为那些字是界面上的；解释放帧外 |
| 给 `localhost` 或内网地址 | 只给确认过能访问的公网地址，否则给文件路径 |

改脚本、改模板时的注意事项见 `references/maintenance.md`。
