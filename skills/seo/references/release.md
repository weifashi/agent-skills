# 发布、核对、上线清单

## 发布前

1. **确认线上现状和发布记录一致。** 如果项目的发布工具会核对「线上文件」和「本机记录」，它报不一致时停下来查清，不要绕过。常见原因是别的会话或别的机器用旧记录发过一次，把之后的文件冲掉了。
2. **只带上自己的改动。** 多人或多个 AI 会话共用一个仓库时：
   - 从已提交的代码构建，不从正在编辑的工作区构建；
   - 发布前比对「改动前的代码构建出来的结果」和线上是否一致。一致才说明这次发布只会带上自己这一处改动。
3. **只发这次涉及的部分**（例如只发官网的静态文件），不顺带发别的应用。

## 发布后

逐项核对，结果如实记录：

| 核对什么 | 怎么核对 |
|---|---|
| 每个页面能打开、标题对 | 逐个请求，看状态码和 `<title>` |
| 测试环境仍然不收录 | 每页都有 `noindex` |
| hreflang 指向的地址都打得开 | 把页面里的 hreflang 地址逐个请求一遍 |
| sitemap 可访问、条目齐 | 请求 sitemap.xml，数条目 |
| 结构化数据能解析 | 取出 JSON-LD 用解析器读一遍 |
| 页面没有排版问题 | 电脑和手机两种宽度截图，看首屏大标题、按钮、要点有没有截断或撑破 |
| 没有横向溢出 | 量页面宽度是否等于窗口宽度 |

截图注意：

- 标题最长的语言最容易出问题，优先看。
- 页数多时把截图拼成总览图，一次看完；没逐页看的要说明「只量了尺寸，没看图」。
- 刚发布的头一两分钟，各地节点可能还在给旧文件，新文件第一次加载也慢。检查脚本要等到页面真的渲染出来（等某个关键元素出现）再量，并在几分钟后复查一次。不要把「还没加载完」判断成「页面坏了」，也不要把「截到了旧版」当成「没生效」。

## 汇报

分三块说清：

- **改了什么**（哪些页面、哪些语言）；
- **核对了什么**（哪些是截图看的，哪些只是程序量的）；
- **没核对什么**，以及要用户决定的事。

## 正式上线清单（写进项目规则）

测试阶段做完后，把下面这份清单放进项目的规则文件或运行手册，并在规则里留一行待办指向它。以后不管谁负责上线都会看到。

**上线当天：**

1. 用上线开关构建官网（去掉不收录、地址换成正式域名、生成 robots.txt）。
2. 核对构建结果：官网部分搜不到 `noindex`；sitemap、canonical 里全是正式域名。
3. 确认 robots.txt 生效，托管平台的默认 robots 或爬虫设置没有把搜索引擎挡掉。
4. 在 Google Search Console（谷歌站长后台）验证域名，提交 sitemap，抽几页做网址检查。需要用户登录账号时，当场说清要登录哪里。
5. 测试环境继续不收录；如果它以前被收录过，在 Search Console 里移除。
6. 打开正式域名的每个页面看源码，确认没有 noindex、canonical 是正式域名。

**上线之后：**

- 第 8 周：看每个页面的展示和点击，决定下一批页面（指南文章、对比页、更多行业页）。
- 第 12 周：主页面的月展示加起来达不到事先定的数（例如 1000 次），就停写新内容，先查技术问题或改投广告。

停止条件要在调研报告里就定好，带数字和日期。新域名通常要几个月才排得上，没有事先定好的标准，很容易一直写下去。
