# 身份、同意和不记的东西

这里写的是工程上的默认做法，不是法律意见。目标国家的规定要单独查（例如欧盟 GDPR、土耳其 KVKK），并在交付时列出「需要法务确认」的点。

## 三级身份

**第一级：单次打开编号**

- 每次打开页面随机生成，只放在内存里，不写进用户设备。
- 不需要同意，因为它不识别个人、也不跨页面跟踪。
- 用它能算：每页被看了几次、看到哪一屏、点了什么、停了几秒。
- 代价：同一个人打开两次是两个编号，所以这一级的数是「人次」。

**第二级：访客编号**

- 用户点了「同意」之后，才在本机存一个随机编号。
- 有了它，同一个人的几次访问、以及之后的注册，能连成一条路线。
- 用户拒绝或撤回时删掉它。

**第三级：账号**

- 不由客户端说了算。后端从登录状态里核对出「这个请求确实是这个账号的」，才把账号编号记到事件上。
- 同意过的访客注册以后，把访客编号和账号对应起来，他注册前在官网的访问也归到这个账号名下。

## 同意框

多数隐私法的共同要求，按这个做基本不会错：

- 只有「拒绝」和「同意」两个按钮，大小一样，位置一样显眼。
- 没选择之前，不写任何非必要的记录。
- 不预先勾选；不能「继续浏览就算同意」；不能不同意就不让看。
- 页脚有入口可以随时改选择。
- 浏览器开了全局隐私控制（GPC）时，当作拒绝。
- 同意的选择本身要存下来，这一条属于必要记录。
- 如果以后要加广告用途（例如保存广告点击编号用于回传），那是另一类用途，要单独的一个选项，不能混在统计的同意里。

统计「同意率」时，只在用户亲手点选的那一刻记一次，不要每打开一页记一次。

## 来源参数

- 推广链接上的 utm 各项、落地页编号、合作伙伴编号，由官网脚本接到站内链接和注册链接上，一路带进产品。
- **写进本机也要等同意**。没同意时只放在当前页面的内存里，够把这一次访问带到注册页就行。
- 没同意的用户，启动时把以前存下的来源记录清掉。
- 只留白名单里的几个参数，每个限长；其它参数一律不要。

## 明确不记

写进表结构的注释和隐私政策里：

- IP 地址（限流用到的来源标识只在内存里做计数，不入库）
- 浏览器型号的原文（只归成手机 / 平板 / 电脑三类）
- 邮箱、电话、姓名、店名
- 地址栏里的参数（路径去掉 `?` 后面的部分再存）
- 表单里输入的内容、搜索词、聊天和语音的原文
- 金额、商品名
- 广告点击编号（除非单独取得了广告用途的同意）

## 不统计的人

- **你客户的客人**：例如商家的顾客扫码点餐的页面、厨房里员工看的屏幕。他们不是你的用户，没有理由被你的推广统计记录。
- **自己人**：给一个开关（例如地址后加一个参数）让这台设备以后都不统计；登录过内部后台的浏览器，后端直接忽略。
- **机器人**：按浏览器标识过滤。

## 保存期限

- 定一个天数（例如 400 天，够看一整年的同比），由定时任务清理。
- 写进隐私政策。

## 隐私政策里要写的

逐类写明：记什么、为什么记、依据是什么（必要 / 同意 / 正当利益）、保存多久、能不能拒绝、怎么行使权利。

用了境外的云服务存这些数据，可能涉及跨境传输的手续。这类属于公司层面的合规事项，不在代码里，交付时单独列给用户。
